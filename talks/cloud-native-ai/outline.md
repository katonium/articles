## スライド構成（1枚1メッセージ）

### Slide 1: タイトル
**AI時代のクラウドネイティブ**

### Slide 2: クラウドネイティブは技術ではなくプラクティスである
- CNCFが定義v1.1(2024年2月)で "technologies" → "practices" に変更
- コンテナやK8sを使っていること自体がクラウドネイティブなのではない

### Slide 3: クラウドネイティブの目的はデリバリー速度と信頼性の向上
- Google Cloudの5本柱: マイクロサービス / コンテナ / DevOps / CI/CD / 宣言的API
- これらは目的を達成するための手段
- 目的: ソフトウェアデリバリーの速度とサービスの信頼性を向上させること

### Slide 4: AIとクラウドネイティブには2つの関わり方がある
- **クラウドネイティブのためのAI**: AIで開発・運用を加速する
- **AIのためのクラウドネイティブ**: AIワークロードをクラウドネイティブの原則で動かす
- 一方通行ではなく相互に強化し合う関係

### Slide 5: AIはアプリケーションのライフサイクル全体を支援する時代になった
- Gemini CLI / Code Assist、Claude Code、Antigravity etc.
- 設計・実装・テスト・デプロイ・運用のすべてにAIが関わる

### Slide 6: AIで速くなるだけでは意味がない
- AIが正しく動くための仕組みと、AIのアウトプットを検証する仕組みが必要
- 3つの実践: コンテキストエンジニアリング / CI/CD / ハーネスエンジニアリング

### Slide 7: コンテキストエンジニアリング — AIに正しく判断させる仕組み
- ガイドラインの整備（CLAUDE.md、コーディング規約等）
- ソースコードや変更履歴へのアクセス
- O11yプラットフォームへの接続（ログ・メトリクス・トレースをAIの判断材料にする）

### Slide 8: CI/CDとハーネスエンジニアリング — AIのアウトプットを検証し、再現する仕組み
- CI/CD: AIの大量アウトプットの妥当性を検証するセーフティネット
- ハーネスエンジニアリング: 繰り返し作業のスキル化。定型タスクをAIが再現可能な形で定義する

### Slide 9: AIワークロードにもクラウドネイティブの原則は適用できる
- コンテナによるパッケージング、オーケストレーションによるスケーリング
- CI/CDによるモデル・エージェントのデプロイ自動化、O11yによる監視
- CNCFは "Cloud Native AI (CNAI)" と定義 — AIはクラウドネイティブの上に乗るもの

### Slide 10: ただし、アプリケーションの特性が変わると設計判断も変わる
- クラウドネイティブの原則は守れる。でも従来のベストプラクティスがそのまま当てはまらない場面がある
- 4つの変化: コスト構造 / ステートフル / 長時間接続 / マルチテナントの粒度

### Slide 11: コスト構造の変化 — API課金が支配的になる
- 従来: コンピュートが主コスト → オートスケールでコスト最適化
- AIワークロード: トークン課金が主コスト → スケールさせるほどAPIコストが線形に増加
- クォータ管理・レートリミットの設計が重要になる

### Slide 12: ステートフルなワークロード — ステートレス前提が通用しない
- コーディングエージェント（Jules、Claude Code on the web等）はセッション状態・ファイルシステムを持つ
- FaaSパターンがそのまま合わない場面がある
- コンテナベースならスケーラブルに構成可能。ステートの永続化戦略が設計課題になる

### Slide 13: ストリーミング・長時間接続 — msではなく秒〜分単位の世界
- LLM呼び出しは秒〜分単位。タイムアウト設計、ストリーミング接続の維持が重要
- リトライ戦略やべき等性の考慮も変わる

### Slide 14: マルチテナントの粒度が変わる — コンテナ単位からセッション単位へ
- 従来のマルチテナント: アプリケーションは1つのサービスアカウントで動き、ユーザー権限はアプリ層で制御していた
- AIエージェント: セッションごとにユーザーの権限で外部リソース（API、ファイルシステム、DB等）にアクセスする必要がある
- Workload Identity（コンテナ単位で1つの権限）では粒度が足りない
- 短時間トークンをユーザー認証後に払い出す、またはユーザーの認証情報をエージェントにパススルーするアーキテクチャが必要
- これはアプリケーション層ではなくミドルウェア/プラットフォーム層で解決すべき課題

### Slide 15: これらは「相性が悪い」のではなく「設計パラメータが違う」
- 原則（スケーラビリティ、レジリエンス、自動化）は同じ
- その原則の実現方法が、アプリケーションの特性に応じて変わるだけ

### Slide 16: ベストプラクティスではなく原則で設計せよ
- クラウドネイティブの目的（デリバリー速度と信頼性の向上）は変わっていない
- AI時代にはベストプラクティスが当てはまらない場面が出てくる
- ベストプラクティスは原則から生まれたもの。前提が変わったら、原則に立ち返って自分で答えを出そう

## 3つの問いへの回答

### この発表の最大の強みは何か
クラウドネイティブの原則とAIワークロードの特性を両方理解した上で、「何が変わり、何が変わらないか」を具体的に示せること。

### 聴衆が最も驚く発見は何か
AIワークロードの設計判断が従来と異なる具体例（コスト構造、ステートフル、長時間接続）。「クラウドネイティブの原則は使える。でもベストプラクティスをそのままコピーしてはいけない」という気づき。

### 5年後でも覚えていてほしいポイントは何か
**「ベストプラクティスではなく原則で設計せよ」**
