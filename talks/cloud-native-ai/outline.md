# AI時代のクラウドネイティブ - Talk Outline

> Google Cloud Jagu'e'r クラウドネイティブ分科会 / 15分 / 15ページ想定

## コアメッセージ

**「ベストプラクティスではなく原則で設計せよ」**

AI時代にクラウドネイティブの5本柱と目的（ビジネスの高速・堅牢化）は変わらない。
しかしアプリケーションの特性が変わることで、設計判断のパラメータは変わる。
既存のベストプラクティスをコピーするのではなく、原則に立ち返って目の前のアプリケーションに最適な設計を自分で考えよう。

---

## 構成

### 1. クラウドネイティブとは（2枚 / 2分）

- クラウドネイティブは**技術ではなくプラクティス**
  - CNCFが定義v1.1で "technologies" → "practices" に変更（2024年2月）
- Google Cloudの定義における5本柱
  - マイクロサービス / コンテナとオーケストレーション / DevOps / CI/CD / 宣言的API
- 目的: ソフトウェアデリバリーの速度とサービスの信頼性を向上させること
  - セルフヒーリング、コスト効率、スケーラビリティはその手段

### 2. AIとクラウドネイティブの関わり方（1枚 / 1分）

- 2つの方向性がある
  - **クラウドネイティブのためのAI**: AIで開発・運用を加速する
  - **AIのためのクラウドネイティブ**: AIワークロードをクラウドネイティブの原則で動かす
- 一方通行ではなく相互に強化し合う関係
- 以降、それぞれを掘り下げる

### 3. クラウドネイティブのためのAI（4枚 / 4分）

AIが開発サイクルをどう変えるか。

- **AI Coding Assistantの台頭**
  - Gemini CLI / Code Assist、Claude Code、Antigravity etc.
  - アプリケーションのライフサイクル全体（設計・実装・テスト・デプロイ・運用）をAIが支援する時代
- **速くなるだけでは意味がない — 3つの実践**
  - **コンテキストエンジニアリング**: AIに正しく判断させるための仕組みづくり
    - ガイドラインの整備
    - ソースコードや変更履歴へのアクセス
    - O11yプラットフォームへの接続（ログ・メトリクス・トレースをAIの判断材料にする）
  - **CI/CDの重要性がさらに増す**: AIの大量アウトプットの妥当性を検証するセーフティネット
    - AIが書いたコードも人間が書いたコードも同じパイプラインで検証する
  - **ハーネスエンジニアリング**: 繰り返し作業のスキル化
    - 定型的な開発・運用タスクをAIが再現可能な形で定義する

### 4. AIのためのクラウドネイティブ（2枚 / 2分）

AIワークロードにもクラウドネイティブの原則は有効。

- AI推論・学習・エージェント開発にもクラウドネイティブの5本柱は適用できる
  - コンテナによるパッケージング・ポータビリティ
  - オーケストレーションによるスケーリング
  - CI/CDによるモデル・エージェントのデプロイ自動化
  - O11yによるAIワークロードの監視
- CNCFも "Cloud Native AI (CNAI)" と定義 — AIはクラウドネイティブの**上に乗る**もの
  - "AI Native" ではなく "Cloud Native AI" という命名の意味

### 5. ただし、設計判断は変わる（4枚 / 4分）★メインパート

クラウドネイティブの原則は守れる。でもアプリケーションの特性が変わるため、従来のベストプラクティスがそのまま当てはまらない場面がある。

- **コスト構造の変化: API課金が支配的になる**
  - 従来: コンピュートリソースが主コスト → オートスケールでコスト最適化
  - AIワークロード: APIのトークン課金が主コスト → スケールさせるほどAPIコストが線形に増加
  - クォータ管理・レートリミットの設計が重要になる
  - 「スケールさせること」自体のコスト感覚が変わる
- **ステートフルなワークロード**
  - コーディングエージェント（Jules、Claude Code on the web等）はセッション状態・ファイルシステムを持つ
  - ステートレスが前提のFaaS/サーバーレスパターンがそのままでは合わない場面がある
  - しかし、コンテナベースであればCloud Run等でスケーラブルに構成可能
  - ステートの永続化戦略（ワークスペースのスナップショット、Gitと会話セッションの保存）が設計課題になる
- **ストリーミング・長時間接続**
  - LLM呼び出しは秒〜分単位のレスポンス。従来のms単位とは異なる
  - タイムアウト設計、ストリーミング接続の維持が重要
  - リトライ戦略もべき等性の考慮が変わる
- **ポイント: これらは「クラウドネイティブと相性が悪い」のではない**
  - 原則（スケーラビリティ、レジリエンス、自動化）は同じ
  - その原則の**実現方法**が、アプリケーションの特性に応じて変わる

### 6. まとめ（2枚 / 2分）

- クラウドネイティブとは「クラウドの力を最大限活用し、高速な開発速度とスケーラブルなアーキテクチャを実現する」ためのプラクティス。この**目的は変わっていない**
- AI時代にはアプリケーションの特性が変わり、ベストプラクティスが当てはまらない場面が出てくる
- **ベストプラクティスは原則から生まれたもの。前提が変わったら、原則に立ち返って自分で答えを出そう**

## 3つの問いへの回答

### この発表の最大の強みは何か
クラウドネイティブの原則とAIワークロードの特性を両方理解した上で、「何が変わり、何が変わらないか」を具体的に示せること。

### 聴衆が最も驚く発見は何か
AIワークロードの設計判断が従来と異なる具体例（コスト構造、ステートフル、長時間接続）。「クラウドネイティブの原則は使える。でもベストプラクティスをそのままコピーしてはいけない」という気づき。

### 5年後でも覚えていてほしいポイントは何か
**「ベストプラクティスではなく原則で設計せよ」**
